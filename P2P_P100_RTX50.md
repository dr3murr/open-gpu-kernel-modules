# PCIe P2P between an RTX 5080 (Blackwell) and a Tesla P100 (Pascal) on the proprietary 580.173.02 driver

> Written with AI coding agents and measured on one machine (RTX 5080 + Tesla P100, Ryzen 9 9950X3D, 64 GB DDR5); not reviewed by a kernel/GPU engineer. Use at your own risk.
>
> Running these two cards together needs a modified driver setup: on Linux, the proprietary R580 driver plus an undocumented module option; on Windows, an INF-edited, re-signed Data Center 582.99 package (see the Basalt fork linked at the end). Nothing here was tested on a stock driver install. The P2P part of this document is Linux-only and also needs patched driver files.

This branch, `p100-rtx50-p2p-580.173.02`, is based on NVIDIA's upstream tag `580.173.02` (commit `20e4e6e`). It documents how CUDA peer-to-peer access (P2P) over PCIe BAR1 was made to work between a GeForce RTX 5080 (GB203, sm_120) and a Tesla P100-PCIE-16GB (GP100, sm_60) in one Linux machine.

Both GPUs have to run on NVIDIA's proprietary driver, whose resource manager (RM) ships as the closed object `nv-kernel.o_binary`. The open kernel modules in this repository support Turing and newer GPUs only (README.md, "Compatible GPUs"), and the P100 is Pascal. So the change that actually runs is a binary patch of the closed RM and of `libcuda.so`. This branch contains the patcher scripts, the same RM change in source form, configuration files, install and rollback scripts, and test programs. It contains no NVIDIA binaries: the scripts patch the files of your own driver install.

## Layer A: running both GPUs (no P2P)

Blackwell GPUs normally need NVIDIA's open kernel modules and Pascal GPUs need the proprietary ones. NVIDIA's [blog post on the move to the open modules](https://developer.nvidia.com/blog/nvidia-transitions-fully-towards-open-source-gpu-kernel-modules/) says Blackwell requires the open modules, and also: "For mixed deployments with older and newer GPUs in the same system, continue to use the proprietary driver." For a Blackwell + Pascal machine those two rules conflict, so it has no supported configuration. On the proprietary R580 driver, the refusal to initialize the GB203 is in the closed RM, and the undocumented registry key `Rm4598628=0xbf5ae9c6` bypasses it [REPORT]. The key was found on 2026-08-23 by static analysis of the closed RM object: the RM reads `Rm4598628` and allows the proprietary initialization of the GPU only if it equals `0xbf5ae9c6`; otherwise it prints the "requires open kernel modules" message [PRIORART]. No public mention of the key was found [PRIORART]. NVIDIA can change or remove it in any driver release.

1. Install the proprietary 580 driver (on Ubuntu: `nvidia-driver-580`, not `nvidia-driver-580-open`).
2. `sudo install -m 0644 p2p-mixed-arch/modprobe/nvidia-coexist.conf /etc/modprobe.d/90-nvidia-coexist.conf`
3. `sudo update-initramfs -u`, reboot, and check that `nvidia-smi` lists both GPUs.

The file contains this line:

```
options nvidia NVreg_EnableResizableBar=1 NVreg_RegistryDwords="RMDisableFeatureDisablement=1;EnableResizableBar=1;Rm4598628=0xbf5ae9c6"
```

What was tested:

- Stock 580.196.07 (NVIDIA CUDA repository packages) with exactly this line ran both GPUs. The test machine ran this way from 2026-11-04, and Basalt's 32 GB-RAM measurements were made on it [REPORT], [SWITCH].
- Stock 580.178.04 ran both GPUs with the full Layer B key set, without any binary patches [REPORT].
- Whether `Rm4598628` alone is enough, without `RMDisableFeatureDisablement` and the two resizable-BAR settings, was never tested.
- In August an `nv.c` patch was applied that skips a module-type check for device ID `0x2c02`. It turned out to be a no-op: the check it skips only refuses self-hosted (Grace) GPUs, whose device-ID ranges do not include the 5080's `0x2c02` [REPORT]. It is not part of this branch.

Do not add the Layer B registry keys or the libcuda patch to an unpatched driver. The script that moved the test machine to a stock driver left the P2P-forcing keys out because, on a stock RM, they can make peer copies report success without moving data [SWITCH]. In August, a patched libcuda on top of the not-yet-patched RM enabled peer access, and a 64 MiB peer copy then reported success while 66,845,461 of the 67,108,864 destination bytes were wrong [PROBE-LOGS]. Before the static-BAR1 part of the RM patch existed, copies also returned success without changing memory [STATUS].

### Closed RM

The closed RM contains compiled versions of the same functions as `src/nvidia` in this repository, plus the pre-Turing code paths that the open RM lacks. Its symbol names are obfuscated; the patcher's table maps the ones it touches (for example, `_nv046768rm` is `nvGpuOpsBuildExternalAllocPtes`). Before it writes anything, it checks the input hash and every symbol address and size, relocation type, target and addend, and original instruction byte that it relies on [STATUS].

1. **Pascal P2P dispatch and BAR1-P2P HAL.** The Pascal create and remove P2P dispatcher slots are pointed at the later-generation dispatchers, which have the same signature and already handle `_CONNECTION_TYPE_PCIE_BAR1`. The five BAR1-P2P HAL functions (get DMA info, create mapping, remove mapping, query mapping, support predicate) are pointed from their default "not supported" stubs to the GH100 implementations.
2. **Peer PTEs.** Peer memory is mapped through the remote GPU's BAR1 bus address (`gpumgrGetGpuPhysFbAddr` of the GPU that owns the memory), with a non-coherent system-memory aperture (`SYS_NONCOH`) in both the GMMU v3 PTE format (Hopper and later, here the 5080) and the older format (here the P100). The address goes into the sysmem address field. The original peer-index and fabric-address path is bypassed. This is done in both the PTE builder and the physical-address builder that UVM uses.
3. **Static BAR1 on Pascal.** The six default static-BAR1 stubs (support predicate, enable, disable, increase and decrease refcount, get static FB aperture) are pointed at the existing TU102 implementations. [STATUS] calls this the decisive missing piece: without it, CUDA silently created the proprietary mailbox peer object and copies returned success without changing memory. With it, RM exposes these BAR1 DMA ranges: RTX-visible P100 range at `0xf800000000`, size `0x3f8c00000`; P100-visible RTX range at `0xf020000000`, size `0x3dde00000` [STATUS].

The HAL redirects are not P100-specific. In the closed RM's KernelBus initializer, every chip that takes the default branch of those HAL selections gets them. Only the 5080 + P100 pair was tested.

### libcuda

Three exact-byte edits; the patcher checks the input hash and the original bytes [STATUS], [REPRO]:

- **Mixed-architecture peer predicate** (file offset `0x2c2276`, `74 44` to `eb 44`). libcuda's internal peer predicate continued only when both GPUs had the same architecture code. The `je` becomes `jmp`, so `cuDeviceCanAccessPeer` and peer enablement accept the Blackwell + Pascal pair.
- **`CU_DEVICE_P2P_ATTRIBUTE_ACCESS_SUPPORTED`** (a 22-byte case at `0x1ab16a`, written over the old case and the padding around it, and one jump-table entry at `0x117e1a4`). Stock libcuda answers this attribute from a cached value, which still said 0 after the predicate edit (`canAccessPeer=1 access=0` [PROBE-LOGS]). The patch sends only this attribute through the same live predicate. The native-atomic, array-access and performance-rank attributes keep NVIDIA's logic.

### UVM header

`uvm_gpu.h-coherence.patch` makes `uvm_parent_gpu_is_coherent()` return `true`. This override is ported from aikitoria's 580.105.08-p2p branch. The comment in the patched header says that the stock memory-window test classifies this mixed Pascal/Blackwell pair inconsistently and keeps UVM off the coherent path.

The patch is for the header in the DKMS source tree that the proprietary driver package installs. The `kernel-open/nvidia-uvm/uvm_gpu.h` of this repository at the same tag is a different file (SHA-256 `11f5a418…`; for example it has an HMM `devmem` field that the package copy lacks), so this change is kept as a patch file and not committed to `kernel-open/`. It does apply to the `kernel-open` copy with a 4-line offset (`patch --dry-run`), but the open modules cannot drive a P100.

### Module options

`modprobe/nvidia-p2p-mixed-arch.conf` (installed as `/etc/modprobe.d/90-nvidia-p2p-mixed-arch.conf`):

```
options nvidia NVreg_EnableResizableBar=1 NVreg_RegistryDwords="RMDisableFeatureDisablement=1;EnableResizableBar=1;Rm4598628=0xbf5ae9c6;ForceP2P=0x11;RMForceP2PType=1;RMPcieP2PType=1;PeerMappingOverride=1;RMForceStaticBar1=1"
options nvidia_uvm uvm_peer_copy=virt uvm_enable_debug_procfs=1
```

| Option | Meaning | Source |
|---|---|---|
| `NVreg_EnableResizableBar=1`, `EnableResizableBar=1` | The driver tries to resize BAR1 to the framebuffer size. | `nv-reg.h` |
| `RMDisableFeatureDisablement=1` | Not defined in the open source. It was in every tested configuration; its effect was not isolated. | |
| `Rm4598628=0xbf5ae9c6` | Undocumented. Lets the closed RM initialize the GB203 (Layer A). | [REPORT] |
| `ForceP2P=0x11` | P2P read enabled (bits 1:0 = 1), write enabled (bits 5:4 = 1), atomics bits 9:8 = 0, so atomics stay disabled. | `nvrm_registry.h` |
| `RMForceP2PType=1` | Force PCIe P2P. | `nvrm_registry.h` |
| `RMPcieP2PType=1` | Use BAR1 P2P instead of mailbox P2P. | `nvrm_registry.h` |
| `PeerMappingOverride=1` | Described as "the WAR for bug 1630288 where we disable 3rd-party peer mappings". The August configuration comment describes it as permitting unprivileged peer mappings. | `nvrm_registry.h` |
| `RMForceStaticBar1=1` | Map the whole framebuffer into BAR1 statically. If BAR1 is too small to map all of it, GPU initialization fails. | `nvrm_registry.h` |
| `uvm_peer_copy=virt` | Pascal is hardwired to virtual peer-copy addressing in R580 UVM, while Blackwell defaults to physical addressing; a mixed pair must use one mode. | August configuration comment |
| `uvm_enable_debug_procfs=1` | Only adds UVM debug files under `/proc`. It was set on the test machine and is not needed for P2P. | |

## Source commits and the binary patch

The two RM commits on this branch are the source form of the closed-RM patch:

- `dfcfa36` is the August source diff, applied unchanged with `git apply -p1`. The four resulting files are byte-identical to the patched tree that diff was made from. Most of it is aikitoria's 580.105.08-p2p RM patch ported to 580.173.02; the six static-BAR1 redirects were added on top.
- `fbbb7af` changes the GMMU v3 peer aperture from `SYS_COH` to `SYS_NONCOH`. The August diff, like aikitoria's patch, wrote `SYS_COH` there. The binary patch that was installed and tested writes `SYS_NONCOH` in both PTE formats, and its comment says "Blackwell must not encode a Pascal peer as SYS_COH". This commit makes the source match the binary.

| Change | Closed RM (`patch_closed_rm_p2p.py`) | Source (this branch) |
|---|---|---|
| Pascal dispatcher accepts `PCIE_BAR1` | 2 relocations: the Pascal create/remove dispatcher slots point to the later-generation dispatchers | `kern_bus_gp100.c`: a `PCIE_BAR1` branch in `kbusCreateP2PMapping_GP100` and `kbusRemoveP2PMapping_GP100` (as in aikitoria's patch) |
| BAR1-P2P HAL | 15 relocations (5 functions, 3 sites each) to the GH100 functions | `g_kern_bus_nvoc.c`: 5 default assignments to `_GH100` |
| Static-BAR1 HAL | 19 relocations (6 functions, 3 or 4 sites each) to the TU102 functions | `g_kern_bus_nvoc.c`: 6 default assignments to `_TU102` |
| Peer PTE address field | 1 byte in `gmmuFmtPtePhysAddrFld` | `gmmu_fmt.c` |
| Peer PTE aperture | 2 detours to a small helper, written over the bypassed peer block, that maps `PEER` to `SYS_NONCOH` (3 code edits, 1 relocation fixup) | `nv_gpu_ops.c` (`SYS_NONCOH` in both formats after `fbbb7af`) |
| Peer PTE base address | The old peer block in the PTE builder and in the inlined physical-address builder now calls `gpumgrGetGpuPhysFbAddr` on the memory's GPU (2 code edits, 3 relocation fixups) | `nv_gpu_ops.c`: the caller computes `bar1BusAddr` and passes it in; the old peer block is under `#if 0` |

The routing for `PCIE_BAR1` is the same in both; the mechanism differs for the dispatcher and for where the base address is computed. aikitoria's patch also changes `kernel_bif.c` (P2P defaults), `nv-pci.c` (the resizable-BAR registry check), `mem_desc.c` and `io_vaspace.c` (assertions). Those changes are not ported. The test machine sets the P2P type and resizable BAR with the registry keys above instead.

The source was compile-checked, not run. `make -C src/nvidia -j16` at this branch built `nv-kernel.o` (exit code 0, no compiler warnings, the four changed files included) with GCC 13.3 [BUILD]. The same four files at the tag also compiled without warnings.

## Install (Ubuntu, DKMS)

Requirements:

- x86_64 Ubuntu with the driver packages `580.173.02-0ubuntu0.26.04.1` installed (`nvidia-driver-580`, `nvidia-dkms-580`, `nvidia-kernel-source-580`, `libnvidia-compute-580` and the rest of the 580 set at the same version), built by DKMS for your kernel. Tested on Ubuntu 26.04. The test machine got them from Ubuntu's `resolute-updates/restricted` archive [INSTALL-LOG]. Once Ubuntu replaces that version, the same packages are listed on Launchpad: https://launchpad.net/ubuntu/+source/nvidia-graphics-drivers-580/580.173.02-0ubuntu0.26.04.1
- Resizable BAR enabled in the firmware setup, so that the 5080's BAR1 can cover all 16 GiB. Both GPUs had 16 GiB BAR1 windows [STATUS]. Smaller BAR1 sizes were not tested, and `RMForceStaticBar1=1` makes GPU initialization fail if BAR1 cannot map all of the memory.
- `iommu=pt` on the kernel command line, as on the test machine [STATUS]. Other IOMMU modes were not validated with the final patch set. aikitoria's README says IOMMU virtualization has to be disabled for this kind of patch.
- `python3`, `python3-pyelftools`, `patch`, `dkms`, and headers for the target kernel.
- SSH or a text console, in case the rebuilt module does not load.

Steps:

```bash
git clone --depth 1 --branch p100-rtx50-p2p-580.173.02 https://github.com/dr3murr/open-gpu-kernel-modules
cd open-gpu-kernel-modules/p2p-mixed-arch
sudo apt-get install python3-pyelftools patch dkms
sudo ./install-p2p-580.173.02.sh        # optional argument: kernel version (default: running kernel)
sudo reboot
```

`install-p2p-580.173.02.sh`:

1. Refuses to run unless `/usr/src/nvidia-580.173.02/nvidia/nv-kernel.o_binary`, `/usr/src/nvidia-580.173.02/nvidia-uvm/uvm_gpu.h` and `/usr/lib/x86_64-linux-gnu/libcuda.so.580.173.02` have the stock hashes above.
2. Builds the three patched files in a temporary directory and checks their hashes against the tested outputs.
3. Saves the stock files (and any existing P2P or coexistence modprobe file) to `/var/backups/nvidia-p2p-mixed-arch-<date>/` and records that path in `/var/backups/nvidia-p2p-mixed-arch.last`.
4. Installs the patched files, runs `ldconfig`, replaces `/etc/modprobe.d/90-nvidia-coexist.conf` (if present) with `/etc/modprobe.d/90-nvidia-p2p-mixed-arch.conf`.
5. Runs `dkms build` and `dkms install --force` for `nvidia/580.173.02` and `update-initramfs -u`.
6. Puts the installed 580.173.02 packages on hold, so that an update cannot silently overwrite the patched files.

The install and rollback scripts are cleaned-up versions of the commands that were run on the test machine in August and November 2026. They have not been run on a real system. They were run end to end in a sandbox, from a fresh clone of this branch: the system paths were redirected into a temporary directory, and `dkms`, `update-initramfs`, `ldconfig`, `apt-mark` and `modinfo` were stubs [SANDBOX]. There, the install produced the three tested hashes, replaced the Layer A modprobe file with the Layer B one and would have held the right packages; a second install run refused (files already patched) and changed nothing; the rollback restored the stock hashes and the Layer A file. The manual equivalent, as root, from `p2p-mixed-arch/`:

```bash
S=/usr/src/nvidia-580.173.02
L=/usr/lib/x86_64-linux-gnu/libcuda.so.580.173.02
sha256sum $S/nvidia/nv-kernel.o_binary $S/nvidia-uvm/uvm_gpu.h $L     # compare with the stock hashes
mkdir -p /var/backups/nvidia-p2p && cp -a $S/nvidia/nv-kernel.o_binary $S/nvidia-uvm/uvm_gpu.h $L /var/backups/nvidia-p2p/
python3 patch_closed_rm_p2p.py $S/nvidia/nv-kernel.o_binary /tmp/nv-kernel.o_binary.p2p
python3 patch_libcuda_peer_arch.py --source $L --output /tmp/libcuda.so.580.173.02.p2p
sha256sum /tmp/nv-kernel.o_binary.p2p /tmp/libcuda.so.580.173.02.p2p    # compare with the patched hashes
install -m 0644 /tmp/nv-kernel.o_binary.p2p $S/nvidia/nv-kernel.o_binary
install -m 0644 /tmp/libcuda.so.580.173.02.p2p $L && ldconfig
patch -p1 -d $S < uvm_gpu.h-coherence.patch
install -m 0644 modprobe/nvidia-p2p-mixed-arch.conf /etc/modprobe.d/90-nvidia-p2p-mixed-arch.conf
dkms build -m nvidia -v 580.173.02 -k "$(uname -r)" --force
dkms install -m nvidia -v 580.173.02 -k "$(uname -r)" --force
update-initramfs -u -k "$(uname -r)"
reboot
```

A process that already has the old libcuda mapped keeps using it until it restarts; replacing libcuda alone needs no reboot [STATUS].

### Handoff round trips [REPORT]

Measured with `p2p_lat.cu` on the patched 580.173.02 (the P2P variant cannot run without it). One handoff from the 5080 to the P100 and back:

| Method | Round trip |
|---|---:|
| CPU in the loop: the 5080 rings a host flag, the CPU launches a P100 kernel, waits for it and rings the 5080 back | 12.1 µs |
| Persistent kernels on both GPUs polling flags in host-mapped memory (no P2P needed) | 4.3 µs |
| Persistent kernels, each flag in the other GPU's memory (P2P) | 2.8 µs |

On the 5080, host-mapped polling only worked with `ld.acquire.sys`; `ld.global.cv` never saw the update [REPORT].

### Atomics and stream memory operations

- Native peer atomics are not available: `CU_DEVICE_P2P_ATTRIBUTE_NATIVE_ATOMIC_SUPPORTED=0` in both directions, and `cuDeviceGetP2PAtomicCapabilities` reports nothing [LATENCY]. The P100 advertises `AtomicOpsCap: 32bit- 64bit- 128bitCAS-`, so it cannot complete a PCIe AtomicOp, and the chipset switch ports on its path advertise `AtomicOpsCap: Routing-` [LATENCY]. `ForceP2P=0x11` leaves atomics disabled. Changing it to `0x111` or patching the reported attribute would only make software advertise atomics that the hardware path cannot carry. No atomic operation over the link was attempted, because an unsupported one could cause an AER event or a GPU fault [LATENCY].
- Stream memory operations (V2 API) [MEMOPS]: `cuStreamWriteValue32` and `cuStreamWaitValue32` work in both directions, on local and peer memory. The 64-bit variants work only on streams of the 5080 (on either GPU's memory) and return `CUDA_ERROR_NOT_SUPPORTED` on the P100. `CAN_FLUSH_REMOTE_WRITES` is 0 on both GPUs.

## Who needs P2P

- **llama.cpp, Qwen3.8-27B split across both GPUs** ([QWEN38_27B.md](https://github.com/dr3murr/llama.cpp/blob/qwen38-27b-p100/QWEN38_27B.md)). Its exact-prefill streamed attention keeps the KV cache on the P100 and streams bounded tiles to the 5080 with layout-transforming peer copies. In the August fork that runtime looks for a Blackwell GPU with peer access in both directions and returns `cudaErrorNotSupported` without one [27B]. When it was added, the exact cold-prefill gate went from 149.819 to 160.370 tokens/s on the layout of that time [27B]. For the rest of that split, see QWEN38_27B.md.
- **Basalt does not use P2P** ([PASCAL.md](https://github.com/dr3murr/basalt/blob/pascal-tier/PASCAL.md)). It never enables peer access: the decode path goes through mapped host memory, and its few `cudaMemcpyPeer` copies are staged through RAM [REPORT]. With about 48 handoffs per token, removing the CPU from the handoff would save about 0.4 ms of about 21 ms per token, and P2P flags on top of that about 0.07 ms (0.3%) [REPORT]. Basalt needs only Layer A; its 32 GB-RAM results were measured on stock 580.196.07 with the coexistence options [REPORT].
- The P100 kernels on the llama.cpp `p100-qr0n` branch are documented in [P100.md](https://github.com/dr3murr/llama.cpp/blob/p100-qr0n/P100.md).

## Rollback

```bash
cd p2p-mixed-arch
sudo ./rollback-p2p-580.173.02.sh       # optional arguments: backup directory, kernel version
sudo reboot
```

It checks that the saved files have the stock hashes, puts them back, replaces `/etc/modprobe.d/90-nvidia-p2p-mixed-arch.conf` with the Layer A file `/etc/modprobe.d/90-nvidia-coexist.conf`, rebuilds the DKMS modules and the initramfs. It keeps the Layer A options on purpose: on the proprietary driver the 5080 needs `Rm4598628` to initialize at all, so if it drives your display, removing all options leaves you without one. The packages stay on hold until you run `apt-mark unhold` on them.

Other ways back:

- Reinstall `nvidia-kernel-source-580` and `libnvidia-compute-580` at `580.173.02-0ubuntu0.26.04.1`, which restores the stock files, then rebuild with `dkms build`/`dkms install --force` and `update-initramfs -u`, and replace the P2P modprobe file with `nvidia-coexist.conf`.
- Move to a newer stock R580 driver with only the Layer A options. On 2026-11-04 the test machine went to stock 580.196.07 from NVIDIA's CUDA repository this way [SWITCH].

## Upgrades

- An update of `libnvidia-compute-580` replaces the patched libcuda, and an update of `nvidia-dkms-580` or `nvidia-kernel-source-580` replaces the patched RM and UVM header [STATUS]. That is why the install script holds the packages.
- A new kernel should build its modules from the patched DKMS source tree [STATUS]. On the test machine the November reinstall rebuilt explicitly for 7.0.0-31-generic with `dkms build`/`dkms install --force` [INSTALL-LOG]; check `dkms status` after a kernel update.
- Do not run the patchers against any other driver build. They refuse to, and their offsets, symbols and relocations would have to be re-audited for a new build.
- CUDA 13's nvcc no longer emits Pascal cubins. The R580 driver still runs P100 code and its PTX JIT accepts sm_60 PTX [STATUS], so P100 kernels need CUDA 12.x or PTX.

## Caveats

- Version-locked: exactly 580.173.02 as packaged by Ubuntu (`0ubuntu0.26.04.1`). The patchers fail closed on anything else.
- Only one machine and one GPU pair were tested. The HAL redirects affect every chip that takes the default branch in the closed RM.
- No native peer atomics (`nativeAtomic=0`), and no 64-bit stream memory operations on the P100.
- Bandwidth is limited by the P100's PCIe 3.0 x4 link behind the chipset.
- Security: with `iommu=pt` the GPUs write directly to each other's BAR1 physical addresses, and `PeerMappingOverride=1` relaxes a peer-mapping restriction. aikitoria's README warns that this setup is dangerous when you run untrusted software or devices.
- Secure Boot was not tested; the DKMS build on the test machine did not sign the modules [INSTALL-LOG].
- `RMForceStaticBar1=1` needs a BAR1 at least as large as each GPU's memory.
- Written by AI coding agents; not reviewed by a kernel or GPU engineer.
